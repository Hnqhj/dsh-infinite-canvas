# 把 NexusVault 无限画布接入 DSH 右侧栏 —— 分析与可执行方案

> 侦察日期：2026-10-02
> 侦察对象：`https://cnb.cool/hjqn/ai-tansuobianjibu`（NexHub / NexusVault，Go + Vue3）＋ 本机 DSH 桌面端 `F:\DSH`
> 结论一句话：**画布可以原封不动保留，右侧栏可以走原生 tab 架构，对话操控可以复用画布已有的 8 条命令契约。** 三者都有现成接口，不需要重写画布。

**实施中被实测推翻/细化的四点**（方案原文没写对的地方）：

1. **`add_card` 的坐标必须落在传入值上。** 第一版 `create()` 只认自动排位、忽略
   `input.x/y`，而真画布的 `addCard(input)` 是从 `input` 里读 x/y 的 —— 冒烟测试
   A3 直接抓到（期望 700，实际 64）。这是**契约级 bug**，不是样式问题。
2. **`/status` 与 `/next` 必须是两个端点。** 自动开面板要求"看一眼队列但别把命令
   取走"，否则一定产生竞态。方案里原本只说了长轮询，没区分读与取。
3. **`.ps1` 必须带 UTF-8 BOM。** 本机是 Windows PowerShell 5.1，无 BOM 的 UTF-8
   中文注释会被按 ANSI 解读，导致字符串字面量断裂、整个脚本语法错误。
4. **传输层必须自启。** 它原本等着占位画布调 `start()`；占位画布一删，
   画布照常渲染、按钮照常能点，但**对话命令全部静默失效且页面上看不出异常**。
   教训见 §12.2。

**仍未验证**（需要重启 DSH）：DSH 是否接受这个 tab 注册、iframe 会不会被信任栅栏
拦下、DSH 主题探测准不准。`client.js` 里为此内置了诊断条（画布脚本 4 秒未就绪就
把 iframe 文档原文摊出来），比反复猜快。

## 一、侦察结论

### 1.1 画布那一半（NexusVault）

| 项 | 事实 |
|---|---|
| 源码位置 | `apps/web/src/canvas/`（47 个文件，约 10500 行）＋ `apps/web/src/views/CanvasView.vue`（3259 行） |
| 技术栈 | Vue 3.5 + `@vue-flow/core` 1.48.2 + `@vue-flow/background` + `@vue-flow/minimap` + `@lucide/vue` 图标 |
| 数据持久化 | **纯 `localStorage`**，无后端。键：`nexusvault-canvas-projects`（索引）、`nexusvault-canvas-project.<id>`（每项目一份）、`nexusvault-canvas-active-project`、`nexusvault-canvas-snapshots.<id>`。存档 schema 版本 2 |
| 后端耦合 | **零**。整个 `canvas/` 目录 `grep fetch|axios|api/|useAuth` 结果为空 |
| 已有对话操控接口 | `canvas/mcp/canvas-commands.ts`：8 条命令 + `CanvasCommandContext` 接口。**不 import Vue、不 import Vue Flow**，纯函数 + 接口 |
| 已有桥接层 | `window.nexusvaultMcp.{ onCommand, reply }`（`CanvasView.vue` 的 `declare global` 里声明，由 `desktop/preload.cjs` 注入） |
| 现有链路 | MCP(stdio) → `desktop/mcp-server.mjs` → HTTP `127.0.0.1:<port>/mcp/control`（Bearer）→ Electron 主进程 → `mcp-command` IPC → 渲染层 `runCanvasCommand` → `mcp-result` IPC → HTTP 响应 |

**8 条现有命令**（`CANVAS_COMMAND_ACTIONS`）：
`get_canvas` / `add_card` / `move_card` / `delete_card` / `select_card` / `set_view` / `open_panel` / `run_agent`

**画布与主应用的耦合点只有 3 处**（这是"能不能整块搬走"的关键，答案是能）：

1. **`vue-router`** — `CanvasView.vue` 用 `useRoute()` 读 `?project=`、`useRouter()`；`canvas/window.ts` 顶层 `import { APP_BASE } from '../router'`。
2. **`window.nexusvaultDesktop`**（Electron 窗口桥）— `canvas/window.ts` 已写成可选、有回落（找不到就走同窗口导航）。
3. **全局 CSS 级联** — `main.ts` 按固定顺序加载 27 个样式文件；画布自己的 4 个 CSS（`canvas-fold.css` → `canvas-flow.css` → `canvas-chrome.css` → `canvas-editorial.css`）依赖前面 `design-unify.css`、`editorial-redesign.css` 等下层规则。

> 第 3 点是**最大的落地风险**，也是本方案选择 iframe 隔离而非"塞进 React 组件树"的直接原因。

### 1.2 DSH 右侧栏那一半

| 项 | 事实 |
|---|---|
| 应用本体 | `F:\DSH\DeepSeek Harness.exe`（Electron）。用户 profile：`C:\Users\Administrator\.dsh\profiles\desktop` |
| 右侧栏实现 | `@deepseek-ai/dsh-client-ui-sidebar-right` |
| 右侧栏模型 | **每会话一个停靠面**；`push` / `fullscreen` 两种形态；最多左右两格，分隔条限 20%–80%；布局持久化在 `localStorage` 的 `dsh.sidebar-right.v1.<sessionId>` |
| 原生已有 tab | 文件树（`ui-sidebar-files`）、浏览器（`ui-sidebar-browser`）、终端（`ui-sidebar-terminal`）、文档预览（`ui-sidebar-documentpreview`） |
| 第三方能否加 tab | **能，且官方文档明确背书**（"随包发布的引导类型走的正是别的包的类型走的同一条公开路径，`ui-sidebar-documentpreview` 是活的证明"） |
| 浏览器 tab 怎么承载页面 | `ui-sidebar-browser`：Web 用 `<iframe>`，桌面用 Electron `<webview>`，**明确支持 loopback** |

**插件接入右侧栏的三个原语**（照抄 `ui-sidebar-files` 的写法即可）：

```js
// ① 注册 tab 类型（静态声明）
ctx.effect(() => ctx.sidebarRightTabs.register({
  id: 'dsh-canvas',            // 在 tab 系统里的唯一身份
  kind: 'canvas',              // 页类型，按 kind 打开
  title: () => t('tab.title'), // chip 文字
  guide: [{ id: 'canvas', kind: 'canvas', title: ..., icon: ... }], // 上右侧栏引导页
  keepMounted: true,           // 切 tab / 切会话不重挂载
}), 'dsh-canvas: tab type');

// ② 注册 tab 正文
ctx.effect(() => ctx.slots.inject('sidebar.right.pane.tab', () => ctx.slots.register({
  name: 'sidebar.right.pane.tab',
  key: 'dsh-canvas',           // ← 必须等于 ① 的 id
  locale: NS,
  inject,
}, CanvasBody)), 'dsh-canvas: tab body');

// ③ 打开
ctx.sidebarRight.openTab('canvas', options);
```

**宿主半 ↔ 浏览器半的通道**：本机已有先例可抄 —— `dsh-asset-library` 在宿主半用 `webServer` 注册 `/api/asset-library/*`，浏览器半用**相对路径**访问（即与应用同源），并且每个请求过"浏览器信任栅栏"`ctx.get('connection')`。这是被验证过的第三方可用通道。

## 二、核心矛盾与选型

**矛盾**：DSH 客户端插件是 **React**（无构建，走 `window.__ModuleLoader__.load`），画布是 **Vue 3 + Vue Flow**。

| 方案 | 画布保真度 | 工作量 | 风险 | 判断 |
|---|---|---|---|---|
| **A. 用 React 重写画布** | 低 —— Vue Flow 要换成 React Flow，3259 行视图 + 47 个模块重写，§47–§58 的交互细节必然漂移 | 极大 | 高 | ✗ 否决 |
| **B. iframe 承载原 Vue 画布** | 高 —— 业务代码零改动，只打桩 3 个耦合点 | 中 | 低 | ✓ **推荐** |
| **C. Shadow DOM 里挂 Vue 实例** | 中 —— `Teleport`（灯箱）会逃出 shadow root；全局级联断层；`position:fixed` 与 DSH 打架 | 中 | 中 | ✗ 风险高于收益 |
| **D. 用原生浏览器 tab 打开 loopback URL** | 高 —— 画布零改动 | 极小 | 中 —— 不是"原生画布 tab"（带地址栏），语义不符 | △ 只作 P0 冒烟手段 |

**选 B。** 理由：
- 画布是"视觉资产"，任何重写都会丢设计细节；iframe 是唯一能保证 100% 保留的路。
- **iframe 承载页面是 DSH 官方认可的做法**（原生浏览器 tab 就是这么做的，且支持 loopback）。
- 右侧栏的"原生感"来自 **tab 外壳**（chip、分栏、全屏、拖拽、每会话布局持久化、引导页、快捷键）—— 这些通过原生注册**全部白拿**，与内层是 iframe 还是 React 无关。

## 三、推荐架构

```
DSH 桌面端（Electron）
│
├── 宿主半（Node） 插件 dsh-infinite-canvas / index.js + lib/*
│    ├─ 8 个 Agent 工具：canvas_get / canvas_add_card / canvas_move_card /
│    │   canvas_delete_card / canvas_select_card / canvas_set_view /
│    │   canvas_open_panel / canvas_run_agent
│    ├─ 桥服务：pending Map<requestId, {resolve, reject, timer}>
│    ├─ HTTP 面（挂 webServer，同源，带信任栅栏）
│    │    GET  /api/dsh-canvas/events      → SSE，宿主→浏览器 推命令
│    │    POST /api/dsh-canvas/result      → 浏览器→宿主 回填结果
│    │    GET  /api/dsh-canvas/embed/*     → 托管画布静态包
│    └─ 与 asset-library 同构：inject 留空 + 懒绑定 + ctx.effect 回收
│
├── 浏览器半（React） 插件 dsh-infinite-canvas / client.js
│    ├─ ctx.sidebarRightTabs.register({ id:'dsh-canvas', kind:'canvas', keepMounted:true })
│    ├─ ctx.slots.register({ name:'sidebar.right.pane.tab', key:'dsh-canvas' }, CanvasBody)
│    ├─ CanvasBody（薄壳，约 150 行）：
│    │    ① <iframe src="/api/dsh-canvas/embed/index.html">
│    │    ② 常驻 SSE 订阅（模块级，面板关着也活着）
│    │    ③ 收命令 → postMessage 进 iframe
│    │    ④ 收 iframe 回执 → POST /result
│    │    ⑤ 主题变量注入（读宿主 --dsw-* / --dsh-*，写进 iframe :root，监听变化）
│    └─ ctx.sidebarRight.openTab('canvas') 用于"命令到达时自动拉起面板"
│
└── iframe 内（Vue 3 + Vue Flow）画布 embed 包
     ├─ 新增入口 apps/web/src/canvas-embed/main.ts + index.html（只加不改）
     ├─ 复用 CanvasView.vue 原样挂载，打桩 3 个耦合点：
     │    ① 提供内存路由（createMemoryHistory）替代 vue-router
     │    ② APP_BASE 常量替代 ../router
     │    ③ window.nexusvaultMcp 同形 shim（postMessage ↔ onCommand/reply）
     ├─ CSS 子集按原顺序引入（Vue Flow → fold → flow → chrome → editorial + 字体 + 变量）
     └─ 自己的 localStorage（同源 → 与 DSH 应用共享存储，键名 nexusvault-* 无冲突）
```

**对话操控画布的完整闭环**：

```
模型 → 调用 canvas_add_card 工具（宿主半）
      → 桥服务生成 requestId，挂 pending，推入 SSE 队列
      → 浏览器半 SSE 收到 → postMessage 进 iframe
      → iframe 内 runCanvasCommand(ctx, command) → 卡片真的出现在画布上
      → iframe 回执 postMessage → 浏览器半 → POST /result
      → 宿主半 resolve(requestId) → 工具返回结果给模型
```

**为什么这条链路是对的**：它和 NexusVault 已有的 `mcp-server.mjs → IPC → nexusvaultMcp` 链路是**同一个形状**，只是把 Electron IPC 换成了 SSE + postMessage。画布侧的 `CanvasCommandContext` 实现（在 `CanvasView.vue` 里）**一行都不用改**。

### 4.2 宿主半（`index.js` 骨架）

```js
export const name = 'infinite-canvas';
export const inject = [];   // 没有任何"必须存在才能加载"的服务

export function apply(ctx, config) {
    const state = { web: false, tools: { registered: false, names: [], reason: 'not attempted' } };

    // HTTP 面：懒绑定 webServer，栅栏按请求解析（照抄 asset-library）
    const registerWebSurface = () => {
        if (state.web) return;
        const webServer = ctx.get('webServer') ?? ctx.get('httpServer');
        if (!webServer) return;
        const gate = () => ctx.get('connection');
        ctx.effect(() => registerCanvasRoutes(webServer, gate, bridge), 'canvas: HTTP API');
        state.web = true;
    };
    registerWebSurface();
    ctx.on('internal/service', (n) => {
        if (n === 'webServer' || n === 'httpServer') registerWebSurface();
        if (n === 'tools') void registerTools();
    });

    // Agent 工具：动态 import defineTool，解析不到只丢工具不丢插件
    const registerTools = async () => { /* 同 asset-library：ctx.get('tools') + defineTool */ };
    void registerTools();
}
```

### 4.3 浏览器半（`client.js` 骨架）

```js
window.__ModuleLoader__.load({
  id: 'dsh-infinite-canvas',
  factory(require) {
    const React = require('react');
    const NS = 'infiniteCanvas';
    const TAB_ID = 'dsh-canvas';

    function CanvasBody({ useTabInfo, sessionId, t }) {
      const { tab, sidebar } = useTabInfo();
      const frameRef = React.useRef(null);
      // ① 常驻订阅 + ② postMessage 下发 + ③ 收执回报
      React.useEffect(() => subscribeCommands(sessionId, (cmd) => {
        frameRef.current?.contentWindow?.postMessage({ type: 'canvas:command', ...cmd }, location.origin);
      }), [sessionId]);
      return React.createElement('iframe', {
        ref: frameRef, className: 'dic-frame',
        src: '/api/dsh-canvas/embed/index.html',
        // 同源，因此不设 sandbox，保证 localStorage 可用
      });
    }

    function apply(ctx) {
      ctx.effect(() => ctx.locale.register(NS, { zh, en }), 'canvas: dictionaries');
      ctx.effect(() => ctx.sidebarRightTabs.register({
        id: TAB_ID, kind: 'canvas',
        title: () => ctx.locale.bind(NS)('tab.title'),
        guide: [{ id: TAB_ID, kind: 'canvas', title: () => ctx.locale.bind(NS)('guide.title') }],
        keepMounted: true,
      }), 'canvas: tab type');
      ctx.effect(() => ctx.slots.inject('sidebar.right.pane.tab', () => ctx.slots.register({
        name: 'sidebar.right.pane.tab', key: TAB_ID, locale: NS,
      }, CanvasBody)), 'canvas: tab body');
    }

    return { name: 'infinite-canvas-client', inject: ['slots', 'locale', 'sidebarRightTabs', 'sidebarRight'], apply };
  },
});
```

### 4.4 iframe 内的兼容 shim（画布侧唯一新增的逻辑）

```ts
// apps/web/src/canvas-embed/mcp-bridge.ts
// 目的：让 CanvasView.vue 的 window.nexusvaultMcp.onCommand / reply 原样工作。
// 形状与 desktop/preload.cjs 暴露的完全一致 → 画布业务代码零改动。
const parent = window.parent !== window ? window.parent : null;
const pendingIn = new Map<string, (cmd: any) => void>();

window.nexusvaultMcp = {
  onCommand(callback) {
    const handler = (event: MessageEvent) => {
      if (event.origin !== location.origin) return;      // 同源校验
      const data = event.data;
      if (data?.type !== 'canvas:command') return;
      callback({ requestId: data.requestId, action: data.action, params: data.params });
    };
    window.addEventListener('message', handler);
    return () => window.removeEventListener('message', handler);
  },
  reply(requestId, result, error) {
    parent?.postMessage({ type: 'canvas:result', requestId, result, error }, location.origin);
  },
};
```

## 六、落地前必须实测确认的清单

这 6 条是方案里**唯一还不能 100% 确定**的地方，P0/P1 阶段逐条钉死：

1. **DSH 桌面窗口的文档源** —— ~~是 `http://127.0.0.1:<port>` 还是 `file://`？~~
   - ✅ **已实测确认（2026-10-02）：同源。** 六个 `DeepSeek Harness.exe` 进程里只有 PID 8904 监听端口，即 `127.0.0.1:19387`，是桌面端唯一的 HTTP 端。实测 `GET http://127.0.0.1:19387/api/asset-library/status` 返回**资产库插件自己的 JSON 错误信封** → 插件 HTTP 面与桌面端渲染层**同源**。
   - 结论：iframe 用相对路径 `/api/dsh-canvas/embed/index.html` 即同源；localStorage 共享（`nexusvault-*` 键无冲突）；无 CORS；同源 cookie 自动携带。**且这条路已由资产库插件在生产中使用验证过**（其客户端就是走相对路径 `/api/asset-library`）。
   - 残余风险：需确认桌面端的认证是靠 cookie（同源 iframe 自动带）还是靠注入的 header（iframe 可能拿不到）。若是后者，embed 路由改为路径级放行。
2. **`webServer` 是否支持 SSE 长连接** —— 仍未验。`asset-library` 只用了普通 JSON 端点 + Range 流。
   - 若支持：`GET /api/dsh-canvas/events` 直推。
   - 若不支持：退化为**长轮询**（`GET /api/dsh-canvas/next?since=<seq>`，超时 25 秒返回空）。**命令闭环不依赖 SSE**，这只是传输层选择。
3. **`sidebar.right.pane.tab` 的 Body 能否拿到 `sessionId`** —— 原生文件树 tab 的 body 里有 `sessionId`；我们的 key 是否同权（不同 key 的注入面可能不同）。
   - 拿不到就退回 `ctx.sidebarRight.mounted` 可观察值。
4. **CSS 子集是否足够** —— `design-unify.css`、`editorial-redesign.css`、`blur-parity.css`、`tapnow-visual.css` 里都有直接点名画布选择器的规则（例如 `editorial-redesign.css:806` 钉画布底条、`design-unify.css:421` 让位画布 chrome 体系）。
   - 对策：先带最小子集跑 P1，再用截图比对**逐条捞**必需的补充规则，写进 `canvas-embed/embed-overrides.css`，**不去改那几个全局文件**。
5. **静态资源** —— `data/library-assets.ts` 指向 `public/library-assets/*.png`；`misans` 字体在 `main.ts` 里全局引入。
   - 二者都要随 embed 包一起产出，否则"资产库"面板出空白、字体会回落。
6. **面板未打开时命令怎么办** —— 选择：命令到达时代替用户打开 tab（`ctx.sidebarRight.openTab('canvas')`），还是直接回错。
   - 建议**自动打开**（"用户看不到的内容不算打开"是 DSH 自己的设计取向），但要给个开关。

## 九、画布项目管理放哪（决策）

### 9.1 先纠正前提：DSH 给插件的是**三个面**，不是一个

| 面 | 槽位 | 宽度 | **作用域** | 语义 |
|---|---|---|---|---|
| 左侧栏条目 | `sidebar.panellist`（list） | 图标行 | root | 页面入口，`id` 同时寻址下面的 `main` |
| **主栏全局面板** | `main`（root keyed slot）+ `ctx.layout.selectPanel(id)` | **全宽** | root | **整页替代对话**。`null` 回到会话界面 |
| **右侧栏** | `rightbar` → `rightbar.session` | 窄列（首次 45% 视口宽，上限 70%），可全屏 | **每会话** | 会话的附属工作区 |

`dsh-library`（资料库）与 `dsh-asset-library`（资产库）走的都是第一种 + 第二种：`sidebar.panellist` 图标 ＋ `main` 全宽页面。**它们不在右侧栏里。**

### 9.2 关键约束（已实测确认）：右侧栏与全局面板**互斥**

`ui-sidebar-right/lib/client.js:5874`：

```js
const visible = usePanelInfo((info) => info.activePanelId === null);
```

`ui-layout` 的官方文档同样写着：「右栏的 root 控制器**仅在选中会话界面时**，经 `SessionProvider` 渲染 `rightbar.session`」。

> **含义：`activePanelId` 不为 `null`（例如打开了资料库）时，右侧栏整列不渲染 —— 画布跟着消失。**

这条约束决定了下面所有结论。

### 9.3 结论：分两层，**不给项目管理单开右侧栏 tab**

#### 第一层 —— 项目切换留在画布 tab 内部（P2–P4 就做）

- 画布页只占右侧栏**一个 `canvas` tab**，项目切换用 tab 内部的下拉 / 内嵌抽屉，复用 NexusVault 已有的 `projectMenuList` / `otherProjects` 逻辑。
- 切项目 = 换 tab 的 `projectId` 参数：`ctx.sidebarRight.openTab('canvas', { params: { projectId } })`。同一 `(kind, contentId)` 会被**聚焦**而不是开新 tab，天然符合"一个画布 tab"的形态。
- 「管理全部画布」保持为画布页内的**弹出式全览层**（就是 `CanvasProjectsView` 那套卡片网格 + 搜索 + 重命名/副本/导入），不占 DSH 的 tab 位。

#### 第二层 —— 跨会话总览放进**资料库**（P5 之后评估）

这是唯一语义正确的位置：

1. **作用域对**：画布项目是**跨会话资产**（会话 A 建的画布，会话 B 要能开），而右侧栏是**每会话**的（布局键 `dsh.sidebar-right.v1.<sessionId>`，官方文档："没有会话就没有停靠面"）。把跨会话索引塞进每会话的面板是语义错位。
2. **空间对**：`CanvasProjectsView` 是「工具栏 + 搜索 + 卡片网格（含 mosaic 缩略拼贴）」，需要全宽。右侧栏默认 45% 视口宽，塞进去只能退化成纯文字列表，丢掉缩略图。
3. **归属对**：`dsh-library` 的定位就是「把每次对话、每个项目产出的东西收进一处」，与资产库的差异表写着「归档与复用」。加一个"画布"分类，与现有的文档 / 页面 / 表格 / 图片 / 链接 / 附件并列即可。

**代价必须说清楚**：因为 9.2 的互斥约束，从资料库点一个画布项目**不能直接"右边就看到画布"**。可行动线只有一条：

```js
// 资料库里点击一个画布项目时
ctx.layout.selectPanel(null);                                   // ① 先切回会话界面，右栏才存在
ctx.sidebarRight.openTab('canvas', { params: { projectId } });  // ② 再开画布 tab
```

即「点一下 → 回到对话，画布在右侧展开」。这在 DSH 的模型里是自洽的（"回到生产现场"），但要接受**会跳一下**。

#### 明确不做的两件事

| 不做 | 理由 |
|---|---|
| **给项目管理单独开一个右侧栏 tab** | ① 每会话作用域 → 在会话 B 看不到会话 A 建的项目，**恰好制造了项目管理要解决的问题**；② 窄列装不下卡片网格；③ 出现两个都叫"画布"的 tab 竞争，切换动线反而变长 |
| **给项目管理单独开一个 `main` 全局面板** | ① 面板占着 `main` 时右栏不存在 → **点项目后开不了画布**，必须 `selectPanel(null)` 再 `openTab`，等于绕回对话；② 会在左栏并排出现"资料库"和"画布"两个资产索引页，职责重叠 |

### 9.4 顺带要定的：画布项目集合的**隔离键**

**不要用「一个 DSH 会话 = 一个画布项目」。** 那样换个会话昨天那张画布就找不到了 —— 与项目管理的目的正好相反。

**建议：按 DSH 会话的 `cwd` 隔离**（即 Workspace 的文件夹路径）。理由：
- DSH 自己的层级是 `Workspace（文件夹）→ Session`，画布项目在 NexusVault 里本来也是"项目"级，两者对齐。
- 宿主半可以稳定拿到：`ctx.get('sessions')` → 会话的 `header.cwd`（`dsh-asset-library` 已经在用这条路径）。
- 落法：localStorage 键加 cwd 派生的短哈希后缀，例如 `nexusvault-canvas-projects.<cwdHash>`。

**一个已知缺口**：DSH **没有给第三方插件公开"当前 Workspace"的读取口**（`dsh-client-ui-workspace` 公开的扩展点只有 Session 行 action 与目录选择 slot，`useWorkspaces` 等是包内部 hook）。所以走 `cwd` 是最省事、且不依赖未公开 API 的路子。此条需在 P4 实测确认 `ctx.get('sessions')` 返回的 `cwd` 是否稳定。

## 十、画布本体放右侧栏还是全局面板（决策）

**结论：画布本体放右侧栏。** 而且不是"折中"，是**严格占优** —— 右侧栏是超集，全局面板是它的真子集。

### 10.1 判据一：DSH 自己的落位惯例（硬证据）

把 DSH 自带界面按落位排一遍：

| 谁 | 落在哪 | 性质 |
|---|---|---|
| 文件树（`ui-sidebar-files`） | 右侧栏 | 并行工作面 |
| 浏览器（`ui-sidebar-browser`） | 右侧栏 | 并行工作面 |
| 终端（`ui-sidebar-terminal`） | 右侧栏 | 并行工作面 |
| 文档预览（`ui-sidebar-documentpreview`） | 右侧栏 | 并行工作面 |
| **模型产出物 / 改动对比**（`ui-deliverables`） | **右侧栏** | 并行工作面 |
| 设置（`ui-settings`） | 全局面板 | 离开会话 |
| 插件管理 | 全局面板 | 入口型页面 |
| 资料库 / 资产库 | 全局面板 | 浏览与整理 |

关键证据 —— `ui-deliverables` 官方文档原话：

> 「点击卡片会在**右侧 Sidebar** 预览文件」「把收尾正文中匹配的行内代码引用转为链接，让被点名的文件在**右侧 Sidebar** 中打开」「每一行通过 `ctx.sidebarRight.openResource` 打开……」

**规律**：
- **与对话同时可见的并行工作面 → 右侧栏**（DSH 全部 5 个原生工作面都在这里，连"模型产出物"都在）
- **离开会话去做一件事 → 全局面板**（设置、插件管理、资料库 —— 全是"入口型页面"）

画布是**并行工作面**：一边对话一边摆卡片。它与"文档预览"同类，而且比它更该在右侧栏 —— 产出物本来就堆在画布上。

> 顺带一个统计佐证：整份 `app.asar` 里 `slots.inject("main")` 只出现 **3 次**。全局面板本来就是稀有用法。

### 10.2 判据二：操作需求 —— 全局面板的致命伤

原始需求是「**让我的 DSH 对话可以操控这个画布**」。这句话隐含两个动作：

1. 我说话 → 画布变化
2. **我看着它变**

全局面板满足 1，**杀死 2**：面板占着主栏时对话不可见。工具在哪张卡片上做了什么、有没有搞错、下一步该说什么 —— 全看不到。等于「闭着眼睛让 AI 改画布，改完再切回去验收」，来回切页面的成本比操作本身还高。

更糟的是：全局面板打开时**右侧栏整列消失**（见 9.2 的互斥约束）→ 画布工作时同时失去文件树、浏览器、终端。而画布的素材来源恰恰就是文件（参考图）和浏览器（找参考）。

### 10.3 判据三：右侧栏是超集 —— 这是决定性的一条

担心"窄列不够铺分镜"是合理的，但 DSH 右侧栏**原生支持全屏**（面板控件里的形态切换，`push` ↔ `fullscreen`）：

| 形态 | 右侧栏 | 全局面板 |
|---|---|---|
| 窄列 + 对话可见 | ✓（默认，约视口 45%；1920px 屏上 ≈864px，中栏还剩 ≈776px） | ✗ |
| 宽幅 + 对话不可见 | ✓（全屏形态，合并主栏+右栏宽度，左侧栏保留） | ✓（同宽度） |
| 同时保留文件树/浏览器/终端 | ✓（`push` 形态下全部可用；`fullscreen` 形态下左栏仍在） | ✗（右栏整体消失） |

**所以：右侧栏提供两种形态，全局面板只提供后者，而且在"后者"这个形态下全局面板还额外丢掉了整个右侧栏。** 全局面板在画布这件事上没有任何一项是右侧栏做不到的。

具体落法：**右侧栏为主 + 全屏为增强**。

- 平时：窄列并存，一边看对话一边看画布。
- 需要全宽做复杂编排：一键全屏，操作完 Esc 退回。
- 两个面都不用改，全是原生原语，零额外实现。

### 10.4 判据四：状态与生命周期

| | 右侧栏 | 全局面板 |
|---|---|---|
| 布局持久化 | **按会话持久化**（`dsh.sidebar-right.v1.<sessionId>`），刷新后 tab 与布局恢复 | **瞬时状态** —— DSH 文档明说「重新加载会恢复侧栏默认值并隐藏右侧面板」 |
| 切走时 | `keepMounted` 可保留正文，不重挂载 | 整页卸载 |
| 多实例 | `multiple: true` 支持独立实例；最多左右两格可并排（画布 + 文件树） | 单实例 |

画布是"要长期摆着"的工作面，全局面板的瞬时性靠不住。

### 10.5 唯一要认真对待的反对意见

如果你的实际用法是「**画布为主、对话为辅**」（一坐两小时在画布上排分镜，对话只是偶尔下指令），全宽的价值会压过并存的价值 —— 你要的是沉浸式工作台。

但**这个场景右侧栏也覆盖**：切到全屏形态就是沉浸式工作台，宽度与全局面板相同。区别只在于右侧栏还多给了你一个"退回窄列看对话"的选项，而全局面板是从头到尾没有这条退路。**能全屏的东西不能变成窄列，但能变窄列的东西可以全屏。**

### 10.6 那全局面板对画布还有没有用武之地

有一个，但**不是画布本体**：**画布总览 / 管理**（选择动作，不是生产动作，替代对话可接受）。不过 9.3 已论证放在**资料库**里更好（职责不重叠、全宽页面骨架已存在）。结论不变。

### 10.7 落地要点（本决策带出的实现细节）

1. `ctx.sidebarRightTabs.register({ id: 'dsh-canvas', kind: 'canvas', title, guide, keepMounted: true })`。
2. 正文 iframe 需要处理**容器尺寸变化**：右栏从窄列拖宽、切全屏、开合分栏都会改变 iframe 尺寸，而 `keepMounted` 下不重挂载 → 用 `ResizeObserver` 观察容器并向 iframe 发 `canvas:resize`，画布侧触发 `useVueFlow()` 重算与 `fitView`。

## 十二、P1：把真画布搬进来（实施结果）

`board.js` / `board.html` 已删除，`lib/embed/index.html` 现在是
**Poiesis / NexusVault 的画布本身**。这一节记三件后来才测出来、光看代码看不出来的事。

### 12.1 闭包比想象中小得多

侦察时的结论（§1.1）是「画布那一半是 45 个文件、外部依赖 6 个包」。实测复核：

| 项目 | 实测值 |
|---|---|
| `canvas/` 目录 | 47 个文件（含 6 个 `*.test.ts`，不进构建） |
| 整个闭包 | 116 个上游文件、约 1.4MB 源码 |
| 外部包（真依赖） | `vue` `vue-router` `@vue-flow/{core,background,minimap}` `@lucide/vue` |
| **对后端 API 的调用** | **0 次**（`canvas/` 下 `fetch(` 命中数为 0） |
| 逃出 `canvas/` 的 import | 4 处，全部好解决 |

「零次网络请求」这一条是决定性的：画布的全部状态在 `localStorage`
（实测键名 `nexusvault-canvas-projects` / `nexusvault-canvas-project.<id>` /
`nexusvault-canvas-active-project`）。所以把它搬进 DSH **不需要任何后端**，
也解释了两件事——按钮为什么能真按下去、以及为什么截图里 `canvasReady` 一亮
就代表链路通了。

逃出的 4 处：

| 上游写法 | 处理 |
|---|---|
| `canvas/window.ts → ../router`（只为拿 `APP_BASE`） | overlay 重写 `router.ts`，`APP_BASE='/app'` 逐字保留 |
| `canvas/window.test.ts → ../router` | 测试文件不进构建 |
| `views/CanvasProjectsView.vue → ../components/PageHeader.vue` | 直接镜像（51 行、零依赖） |
| `views/CanvasView.vue → ../data/library-assets` | 镜像成 `library-assets.data.ts`，overlay 只重写 URL 函数 |

最后一条是刻意的：清单数据继续吃上游那份，**不复制**，所以上游加一张图
下次构建自动有，不会出现「一边加图另一边看不见」。

### 12.2 唯一真正的接入点只有一行

真画布的 `CanvasView.vue` 挂载时自己会调 `window.nexusvaultMcp?.onCommand(...)`
（文件顶部 `declare global` 声明了这个接口）。所以整个接入就是
**抢在它之前把那个名字占住**，其余全都不用碰。

`lib/embed/canvas-transport.js` 原本只有 `install()` 不自启，等着占位画布的
`board.js` 调 `start()`。占位画布一删，那一行也没了——**画布照常渲染、按钮照常
能点，但对话一条命令都进不来，而且页面上看不出任何异常**。
教训：`<canvas 页里除了传输层，没有任何人知道 DSH 的存在，所以自启是传输层自己的事`。

这条不变量现在由测试 B8 钉住：`index.html` 里传输层的内联位置必须早于入口模块，
否则画布注册不上处理器。

另外 `start(options)` 收的是 **options 对象**，传字符串会被静默忽略
（`typeof opts.sessionId === 'string'` 不成立）——会话标识就是这么丢过一次。

### 12.3 目标环境比验证环境新，是最隐蔽的坑

一开始 `build.target` 写的是 `chrome122`（DSH 是 Electron 36 / Chromium 132）。
压缩器据此把 `@media (max-width: 680px)`「现代化」成范围语法
`@media (width<=680px)` —— 范围语法要 **Chromium 104+**。
而本机无头 Edge 是 **Chromium 100**，整条媒体查询被解析成 `not all`、
**永不匹配**：窄屏布局覆盖全部失效，页面看起来「只是有点挤」，不报错。

这条是靠一次探针抓到的，不是看出来的：

```js
// 在浏览器里枚举所有命中某元素的规则，连同它所在的媒体条件
const walk = (rules, ctx) => { for (const r of rules) {
  if (r.type === 4) walk(r.cssRules, r.conditionText || r.media.mediaText)
  else if (r.selectorText?.includes('ref-bottom-left')) out.push([ctx, r.selectorText])
} }
```

返回的最后一条是 `@not all | .canvas-page .ref-bottom-left {10px/70px}`——
**规则在、选择器对、值对，就是媒体条件不成立**。没有这段代码就只能靠猜。

修正：`build.target` 定 `chrome100`，压缩器不再改写语法，于是**验证时看到的
与 DSH 里看到的一致**（DSH 更新，只会更宽松）。

### 12.4 窄容器要改的是布局，不是视觉

上游把三组工具条排在同一 `bottom: 14px`（左 / 居中 / 右三种定位各自躲开），
内容净宽 116 + 190 + 275 = 581px。实测重叠阈值：

| 视口 | 重叠 |
|---|---|
| 520px | 中条 165~355 与右条 227~502 直接压在一起，「100%」被网格图标盖住 |
| 700px | 中条右缘 445 > 右条左缘 407，仍压38px |
| 760px+ | 不重叠 |

解 `视口 ≥ 738`（中条居中故右缘 `= 视口/2 + 95`），取 760px 断点。

空态引导是另一类问题：`.canvas-empty-guide` 是 `position:absolute; left:50%`
且**没给 right** 的 shrink-to-fit 陷阱——绝对定位的可用宽度被算成
「从 left 到容器右缘」即**视口的一半**，520px 时可用 260px，而三个按钮自然宽度约 99px、
共 313px。放不下就触发 flex 收缩，按钮被压到 65px，中文逐字换行互叠。
上游在 ≥740px 的窗口里碰不到这个坑。

两处都由 `build/overlay/src/dsh-shell.css` 在 ≤760px 时改布局：工具条折成两行
（上排 资产库/积分 + 创建条，下排 右侧工具条独占），引导框 `width: max-content`。
实测 380 / 440 / 520 / 700 / 760 / 900 六档**零重叠**，按钮恢复 102px 自然宽度。

### 12.5 因为在 iframe 里，全局 CSS 可以整条搬

画布的观感有一半来自那 33 份「外壳层」样式：`style.css` 的 165 个变量与基础重置、
`blaze-parity.css` 的 Geist `@font-face` 与 `--rd-font-ui`、以及
`design-unify.css` 与 `canvas-flow.css` 之间那对**靠源码顺序决胜的 `!important`**
（上游在 `canvas-flow.css` 注释里专门记过这个坑，还留了一条 probe 脚本钉它）。

iframe 里全局样式**不会外泄**，隔离是免费的。所以选择是「整条照搬」而不是
「挑几份带进来」——后者是在赌「哪几份有用」，赌错的代价正好是用户这次要解决的
「看起来像另一个应用」。

搬进来的代价是三处路径改写（见 README 表格）。其中文源圆体那两个 woff2
各 6.5MB，而该字体在上游**已退役且零引用**（全仓只有 `@font-face` 声明，
没有任何 `font-family` 用它）——换成空 data URI，**若哪天上游重新启用它，
这里必须改成真搬字体**。

MiSans 是分包字体（4 档 × 112 个 unicode-range 子集），Vite 全量输出到
`lib/embed/assets/`，运行时浏览器只拉用到的子集。

### 13.2 DSH 主题的真实机制（三态，但 DOM 只留两态）

官方偏好是 `light` / `dark` / `system` 三值，但**投影到 DOM 的只有解析后的结果**：

| 位置 | 内容 | 出处 |
|---|---|---|
| `html` | `color-scheme`（驱动原生 UA 控件） | ui-layout README「主题呈现」 |
| `body` | `[data-ds-dark-theme]` 属性 + 内联 `--dsw-*` 变量 | 同上 |
| `<meta name="theme-color">` | 随计算后 body 背景色更新 | 同上 |
| 宿主侧 | `matchMedia("(prefers-color-scheme: dark)")` 监听器，解析成不可变 `ThemeSnapshot` | ui-theme README |

**踩坑：旧实现读 `document.documentElement.dataset.theme` —— 属性在 `body` 上，不在 `html` 上**，
`data-theme` 也不是 DSH 的名字（那是上游画布自己的锁）。`MutationObserver` 的
`observe` 目标同样必须从 `documentElement` 改成 `document.body`，否则主题变化永远收不到。

### 13.3 命名空间：颜色是 `--dsw-*`，不是 `--dsh-*`

| 前缀 | 用途 | 实例 |
|---|---|---|
| `--dsw-*` | **颜色**（190 个 token） | `--dsw-alias-bg-base`、`--dsw-static-neutral-bluish-950` |
| `--dsh-*` | 几何与字号 | `--dsh-frame-top-clearance`、`--dsh-windows-content-radius`、`--dsh-content-font-size`、`--dsh-scrollbar-width` |

就是这样一路没发现的。已把诊断条整体迁到 `--dsw-*`。

### 13.4 决策：为什么「传 token」而不是「iframe 里自己声明一套」

官方说 token 表是唯一权威来源。**在 iframe 里复刻一套浅色值，看着像，但和 DSH 实际
解析出来的值只会在某个色阶上不一致 —— 那就不叫"一致"。** 而父页面（`client.js`）
就住在那份权威样式表旁边，`getComputedStyle(document.body).getPropertyValue()`
读出来的就是**当前主题解析后的最终值**，零偏差、零维护。

链路：
```
DSH 设置改动
  → body[data-ds-dark-theme] 变化
  → MutationObserver（observe body）
  → readDswTokens() 读 22 个 token 的计算值
  → postMessage { type:'theme', payload:{ theme, tokens } }
  → dsh-bridge.ts 逐个 root.style.setProperty()
  → 壳层元素 var(--dsw-alias-*) 生效
```

桥的两条安全属性（已用测试 B10 钉住）：
1. **只放行 `--dsw-` 前缀** —— 父页面送来的其他变量名一律不写；
2. **拦掉 `;` `}` `<`** —— 这三个字符能截断后续 CSS 声明。`setProperty` 对
   无法解析的值是**静默丢弃**，所以先做形状校验再写。

### 13.5 首帧闪烁：`color-scheme` 必须由内联脚本先设

`dsh-bridge.ts` 是 ES 模块，要等下载+解析+求值才跑得到。在此之前
`dsh-shell.css` 里那条兜底 `html { color-scheme: light }` 会先生效 ——
DSH 深色下会闪一条浅色滚动条。所以 `index.html` 的 head 里内联读一次
`?theme=` 参数（同源同文档，父页面写好的，首帧就能读），不等桥。

这是**两处**都要设，不是一处：内联脚本防首帧，桥防后续 postMessage 切换。

### 13.6 画布本体为什么仍是深色（已与用户确认）

上游把画布锁死恒深色是**产品决策**（`canvas-flow.css` 有专段解释：图像工作区，
深底更利于判断画面），不是遗漏。用户已确认「先只做外壳，画布保持深色」。

实测边界：注入 DSH 浅色 token 后，`.canvas-page` 背景仍是 `rgb(18, 18, 18)`，
而工具条变成 `rgb(255, 255, 255)` + `rgba(0,0,0,0.04)` 描边 —— 层次清楚，
不是"整个画布被漂白"的假跟随。截图见 `docs/验证-主题-浅色.png` / `docs/验证-主题-深色.png`。

### 13.7 三个坑（都是自己踩的）

**① `build:only` 不含 sync，overlay 改动会静默丢失。**
改了 `build/overlay/src/dsh-bridge.ts` 后只跑 `vite build`，`build/src/` 里
还是上一轮的旧文件（`applyTokens` 命中数 0），产物照样构建成功、照样装进 embed ——
**没有任何一处报错**。改 overlay 后必须走完整 `npm run build`
（`sync-upstream` → `copy-static` → `vite build` → `install-embed`）。

**② 独立打开 embed 页截图，深浅两张图会逐字节相同。**
`?theme=light` 只改 `color-scheme`，父页面不在 → 没人注入 token →
工具条吃 `dsh-shell.css` 的兜底深色值。实测两张都是 120,758 B。
**截图必须走"先注入再截"**（`theme-bridge.mjs` 里的 `shoot()`），否则会得出
"主题桥没生效"的错误结论。

**③ 比 CSS 颜色值不能直接比字符串。**
三种表示法差异会造出假失败：注入的是 `#ffffff` 而元素算出来是 `rgb(255, 255, 255)`；
`0.10` 被浏览器归一成 `0.1`；`0.06` 千万别用 `replace(/(\.\d*?)0+\b/)` 归一
—— 那会把 `0.06` 改成 `06`。正确做法：token 与 token 比（原样字符串，
`getPropertyValue` 不折算），元素颜色与元素颜色比（都过同一个 `normalizeRgb`）。

- `.workbuddy/verify/theme-bridge.mjs`：深浅两态 × 13 项 = **26/26 全绿**，
  覆盖 `data-dsh-theme` / `color-scheme` / 9 个 token 原值 / 画布本体恒深 /
  工具条取到注入值 / 圆角 / 描边
- 已同步 259 个文件到 `~/.dsh/profiles/desktop/node_modules/dsh-infinite-canvas`，

### 13.9 修「还是这样」：token 是**两层**的，只送 alias 层等于没送

**现象**：用户截图显示 DSH 已是浅色，画布区工具条仍是深色。
第一反应是"父页面没注入到"，于是去连 DSH 查——但 DSH 走 `127.0.0.1:19387`
且**要鉴权**（`401 dsh web authentication required`），没有 CDP 端口，网络探不通。

于是改用**离线复现**，一下就抓到了。

#### 根因

DSH 的 token 是**两层**：

```css
body[data-ds-dark-theme] {
  --dsw-static-neutral-bluish-00: #fff;                          /* static：字面量 */
  --dsw-alias-bg-layer-1: var(--dsw-static-neutral-bluish-875); /* alias：引用 */
}
```

而 `readDswTokens()` **只送了 alias 层**。iframe 里拿到
`--dsw-alias-bg-layer-1: var(--dsw-static-neutral-bluish-875)`，但那个
`--dsw-static-*` 在 iframe 里**不存在** → `var()` 断链。

实测三种情形（`.workbuddy/verify/probe-var-chain.mjs`）：

| 情形 | `background` 计算值 |
|---|---|
| 两层都在 | `rgb(255, 255, 255)` ✓ |
| 只给 alias | `rgba(0, 0, 0, 0)` —— **整条声明被丢弃** |
| 只给 alias + 兜底值 | `rgb(21, 21, 23)` —— **吃兜底** |

第三行就是本插件的现象：**工具条恒为深色 `#151517`，而 DSH 已经是浅色**。
看起来像"主题桥没写"，实际是"少送了一层"。

#### 为什么 static 层可以整层搬

实测 77 个 static token **全是字面量、0 个引用**，所以不存在递归解引用的深度问题。
另实测这两个层都定义在 **body 上**（浅色 `body{}` 77 个、深色
`body[data-ds-dark-theme]{}` 77 个），`getComputedStyle(document.body)` 一次读齐。

#### 修法（三处）

1. `client.js`：加 `STATIC_TOKEN_NAMES`（77 条硬编码名单），`readDswTokens()`
   读完 alias 后**再整层读 static**。
2. `build/overlay/src/dsh-shell.css`：`:root` 兜底块**也改成两层**
   （原来只声明 alias，等于"断链 + 兜底"双重保险都没有）。
3. `tools/smoke-test.mjs` B10：加 4 条静态断言，把"static 层必须一起送"
   变成可测事实（名单存在 / ≥70 条 / 真的遍历了 / CSS 兜底也是两层）。

#### 顺带修掉一个"假绿的测试"

`theme-bridge.mjs` 原先的测试数据是**「alias 直接给字面量」**——
这在 DSH 里根本不存在，于是它测的是一个假场景：只送 alias 的写法照样全绿。
已改成两层结构（alias 值写 `var(...)`），断言也改成验**解引用后的结果**：

```
✓ --dsw-alias-bg-layer-1 解引用 → #232324
✓ 工具条底色取到注入值: rgb(35,35,36)
```

> 教训：**测试夹具必须复刻真实的间接层结构**。把 alias 简化成字面量，
> 测的就不是线上跑的那条路径。

#### 验证

- `probe-var-chain.mjs`：三行对照，确认断链与解引用。
- `theme-bridge.mjs`：深浅两态全部通过，alias 逐个解引用成功。
- 离线校验：`STATIC_TOKEN_NAMES` 77 条、命名全合法、在 body 上能读齐。
- `npm test` **38/38**；已同步 259 文件到 profile，`client.js` md5 一致。

## 十四、P2.5：画布浅色化 + 按钮按 DSH 重置

用户 2026-10-02 看到效果后提两点：①画布怎么还是深色 ②按钮怎么还是原设计。
本节记录根因与实施。**这一节推翻了 13.6 的「画布恒深色」决策**，依据见 14.2。

### 14.1 根因一：配色被写进了窄容器断点（我自己的 bug）

上一轮把工具条的 DSH 底色/描边写在：

```css
@media (max-width: 760px) {          /* ← 只有窄容器才命中 */
  .canvas-page .ref-bottom-left { background: var(--dsw-alias-bg-layer-1); … }
}
```

而 DSH 右栏在 1080px 窗口下有 **600+px 宽**（实测右栏占屏 697/1080），
**那条断点根本不匹配** → 工具条一直是上游原样。

> 教训：**断点只管布局，配色要放在断点之外**。
> 这条已写成断言（B10 ⑥），按花括号配对切块后逐块检查。

### 14.2 根因二：「画布恒深色」不是产品决策，是上游的历史遗留

上一轮我读到 `canvas-flow.css` 有「画布页为什么始终是深色」那段注释，
就判断成"刻意的产品决策"。**读完整段才发现结论正好相反**：

> 它确实是**历史遗留而非刻意设计**，若要跟随主题**只需删掉那一段的
> background 覆盖**。

上游说得很清楚：改造前 CanvasView 有两个 style 块，后者无条件
`.canvas-page { background: #101114 }`，按源码顺序盖掉了前一个的
`:global([data-theme='dark'])` 变体；迁移时"保持了这个行为"，但那是**沿用**不是**设计**。

所以浅色化是**修上游的 bug**，不是推翻它的决策 —— 这也让它从"要不要做"
变成"怎么做"。用户拍板：**分层覆盖，先底层后细节**。

### 14.3 浅色覆盖层怎么写

用 `[data-dsh-theme='light']` 而不是 `[data-theme='light']`：
后者是上游的锁（`index.html` 首帧内联钉成 dark），我们不碰；
`data-dsh-theme` 才是本插件写的、跟随 DSH 的那个属性。

覆盖面（第一层，底层）：

| 元素 | 上游 | 浅色下改成 |
|---|---|---|
| `.canvas-page` / `.canvas-stage` | `#121212` + `#e9eaf0` | `bg-base` + `label-primary` |
| 点阵 `pattern circle` | 深灰 | `bluish-200`（同档浅值） |
| `.floating-panel`（8 个面板） | `#202124` | `bg-layer-1` + 发丝描边 + 圆角 12 |
| `.panel-search input` | `color:#fff` | `label-primary` + `bg-layer-2` |
| `.canvas-empty-guide` | `rgba(20,20,20,.97)` | `bg-layer-1` + 浅描边 |
| `.ref-title` / `.ref-topbar` | `#e7e8eb` | `label-primary` |
| minimap | Vue Flow 默认深 | `bg-layer-1` + `mask` 降到 6% |
| 三组工具条 | `transparent` / `#22242b` | `bg-layer-1` + `border-l1` + 圆角 8 |
| 选中描边（涂鸦/文字色） | `outline: 2px solid #fff` | 品牌蓝（白描边在浅色下等于看不见） |

### 14.4 ⚠️ 浅色兜底必须给**三层**，不是两层

`:root` 的深色兜底里 `bg-layer-1` 是 `#232324`、`layer-3` 是 `#353638`（逐层变浅）。
浅色下若照搬这个直觉（layer-1 白、layer-3 更白），**layer-1 与 layer-3 会都变成白**，
于是按钮的悬停/按下反馈**完全消失**。浅色下要给：
`layer-1 #fff` / `layer-2 #f5f6f7` / `layer-3 #ebeef2`。

### 14.5 按钮重置（用户选「只重置视觉」）

按 DSH 官方控件规范，**不重排结构、不换图标**：

- 圆角 `--dsw-radius-xs`（4px，工具条容器 `sm` 8px）；
- 底色 `bg-layer-1`、悬停/按下 `bg-layer-2`；
- 描边 `border-l1`（浅 `#0000000a` / 深 `#ffffff0f`，官方叫"发丝描边"）；
- 焦点环 `--dsw-focus-ring-color` + `--dsw-focus-ring-width: 2px`
  ——上游原本**没有可见焦点态**，键盘用户在这张画布上是迷路的。

### 14.6 对比度扫描：抓出两处「白底白字」

浅色化最容易漏的不是底色，是**深底假设的硬编码**。在 `theme-bridge.mjs` 里加了
一个扫描器：遍历 `.canvas-page` 内所有「有直接文字且可见」的元素，
上溯到第一个不透明背景，算 WCAG 相对亮度差。阈值 1.5（偏松，只抓明显不可读）。

首轮就抓到两处：

| 元素 | 前景 | 背景 | 比值 |
|---|---|---|---|
| `.canvas-empty-title` | `rgba(240,243,241,.9)` | 白 | **1.12** |
| `.credits-trigger b` | `#f0f1f4` | 白 | **1.13** |

第二处的成因值得记：**颜色不从父按钮继承**。我给 `button` 加了
`color: var(--dsw-alias-label-secondary)`，但 `<b>` 有自己的颜色声明，
于是完全无效。修法是逐个点名：

```css
.canvas-page .ref-bottom-left :is(b, strong, i, em, span) { color: …; }
.canvas-page .ref-bottom-left .credits-trigger b { color: …; }
```

找 `<b>` 是怎么定位的：CSS 里 grep 不到（无类名），改用 **CSSOM 枚举命中的规则**
（`el.matches(rule.selectorText)`）才问出是哪一条 —— 见
`.workbuddy/verify/ask-b-element.mjs`。翻源码猜不出来，**该问 CSSOM 就问**。

### 14.7 验证

- `npm test` **38/38**（B10 新增 3 组断言：浅色覆盖层存在 / 断点里无配色 / 两处白底白字已覆盖）

### 15.1 反馈与定位

**病因是两条，不是一条：**

## 16. P2.7：浮层面板内部控件彻底浅色化

### 16.1 根因：上一轮只改了「外壳」，整整漏了一层

用户反馈「控件的颜色怎么还没有改」，并附了两张截图（生成面板的
「图片 / GPT Image 2.5 / 1:1·1K / 4 / ↑」胶囊、提示词区全是深底白字）。

排查发现是**两个叠在一起的漏**：

**漏 1：`.generate-panel` 是唯一不带 `.floating-panel` 类的面板。**
上一轮（浅色化第一层）把 8 个面板的**外壳**统一收进了
`.floating-panel` 覆盖规则，但 `CanvasView.vue:3001` 的

```html
<section v-if="activePanel === 'generate'" class="generate-panel">
```

只有 `generate-panel` 一个类。所以上一轮的覆盖**一条都没碰到它**。
顺带确认 `CanvasView.vue` 里 `activePanel` 的全部取值为
`assets / credits / generate / library / materials / doodle / shortcuts / settings`
共 8 个（其中 `assets` 落不到任何 `v-if`，是上游自己的悬空入口）。

**漏 2：验收扫描只扫了默认可见的元素，面板一个都没扫到。**
`theme-bridge.mjs` 的对比度扫描覆盖 8 个元素（空态引导 + 三组底部工具条），
**全部是默认可见的**。而 7 个面板都是 `v-if` 按需渲染，
打开面板前它们根本不在 DOM 里 —— 扫描器天然扫不到。

> 这是本项目最贵的一个教训：**「扫描全绿」被误读成了「浅色化做完了」**。
> 验收扫描如果不能把目标**打开**，就只验了默认可见的那一层。

### 16.2 新工具：逐个点开再扫

新增 `.workbuddy/verify/scan-panels.mjs` —— 逐个点击 7 个面板的打开按钮，
再扫描面板内每一处的底色 / 文字色 / 对比度。覆盖元素从 **8 个扩到 112 个**。

面板清单用 `[title="…"]` 定位打开按钮，**不用 `nth-child`**：

```js
const PANELS = [
```

用 `nth-child` 的后果实测过：上游改一次按钮顺序，定位就错位，
脚本只报「面板没打开」而不报「按钮点错了」—— **错法是静默的**。

### 16.3 判据要随主题反转

第一版判据只有一条「亮度 < 0.35 = 深色残留」，单跑浅色没问题。
但把它原样拿去跑 `--theme=dark` 报了 35 处「问题」—— 深色主题底本来就该深，
这 35 处全是噪音，真问题直接被淹没。改成：

```js
const WRONG = THEME === 'light' ? (lum) => lum < 0.35 : (lum) => lum > 0.45;
const wrongWord = THEME === 'light' ? '深色残留' : '浅色残留';
```

对比度阈值 `1.5` 两主题同用。这一改反而暴露出深色下 4 处上游
浅色硬编码 + 1 处**两主题都错**的真问题（见 16.5）。

### 16.4 假阳性必须消掉

扫到第 5 个假阳性，人就会懒得看；扫描器一旦失去可信度就等于不存在。
三条设计上正确的豁免：

| 豁免 | 理由 |
|---|---|
| 品牌蓝 `#4176e6` / `#7aaaff` | DSH 官方主色，两主题下都合法 |
| 涂鸦笔刷 `<i>` | 内联 `background` 是**笔迹内容色**，不跟随主题 |
| `input[type=range]` | 浏览器自绘，主题无关 |

另外把「元素是否自有底色」的阈值从 `a > 0.02` 改成 `a > 0.6` ——
`0.02` 会把 `rgba(0,0,0,0.12)` 这种近乎透明的底当成实底，
拿它当参照算出一堆假的「看不清」。

### 16.5 覆盖层做了什么

原来只有一节「浮层面板（8 个共用 `.floating-panel`）」的浅色覆盖，
被**整体重写**为「第二层：把 7 个面板的内部构件也全部浅色化」。

通用容器规则（把 `.generate-panel` 与 `.floating-panel` 一起收）：

```css
html[data-dsh-theme='light'] .canvas-page :is(.generate-panel, .floating-panel) {
  background: var(--dsw-alias-bg-layer-1);
  color:      var(--dsw-alias-label-primary);
  border:     1px solid var(--dsw-alias-border-l1);
  border-radius: var(--canvas-radius-md);
  box-shadow: var(--canvas-shadow-float);
}
```

按面板分组的关键几条：

| 目标 | 上游硬编码 | 覆盖为 |
|---|---|---|
| `.generate-icon` 图标瓦片 | `#2a2d36` | `bg-layer-2` + `border-l2` |
| `.generate-panel textarea` | `color: #fff`（白底白字） | `label-primary` |
| `.generate-pill` / `.generate-cost` 胶囊 | `#1b1d22` | `button-floating-fill` |
| `.generate-pill b` 模型名 | 颜色不继承父胶囊 | `label-primary` 单独点名 |
| `.library-preview` 缩略图占位 | `#141519` | `bg-layer-2`（不能纯白） |
| `.doodle-panel i.selected` | `outline: 2px solid #fff`（浅色下白圈=看不见） | `state-business-primary` |
| `.settings-panel p .switch` | `#eee` | `bg-layer-3` / 开启 `state-business-primary` + `switch-thumb` |
| `.settings-panel p .danger` | `rgba(180,180,180,.12)` + `#c8c8c8`（**对比度 1.24**） | `state-error-primary` |
| `.panel-close` / `header button` | `background: none` + `#8b919e`（深色下几乎看不见） | `label-secondary` + `interactive-bg-hover` |
| `.palette-item` 加节点条目 | 深底 | `bg-layer-1` + `border-l1` |

**主操作按钮**两主题统一用 `state-business-primary`（浅 `#4176e6` / 深 `#7aaaff`）：

```css
html[data-dsh-theme] .canvas-page .generate-submit {
  background: var(--dsw-alias-state-business-primary);
  color: #ffffff;
}
```

不用官方的 `--dsw-alias-button-contrast-fill` —— 夹具补齐后实测它深色下解析为
`bluish-50` = `rgb(249,250,251)`，深底上一个近白圆**非常刺眼**，
而它承担的是主操作位，DSH 深色的主按钮是品牌色。
`button-contrast-fill` 的正确用途是**深底上的次要强调**。

### 16.6 三处「冒用官方前缀」的修正

官方 190 个 token 里**根本没有**这三个名字（README 明说
「设计系统中缺失的值会有意不补入」）：

| 误用 | 官方真身 | 处理 |
|---|---|---|
| `--dsw-alias-state-danger` | `state-error-primary` / `state-error-secondary` | 5 处全换 |
| `--dsw-radius-*` | **无任何 radius token**（`grep radius` 命中 0） | 27 处改自定义 `--canvas-radius-*` |
| `--dsw-alias-...` 里手抄的控件 token | 需连 `--dsw-static-*` **整层搬** | 见 16.7 |

DSH token 是两层：`--dsw-static-*`（77 个字面量）+ `--dsw-alias-*`（值是
`var(--dsw-static-*)` 引用）。跨界传递必须**整层搬**，只送 alias →
`var()` 断链 → 声明被丢弃 → **静默失效**。

顺带记一个选择器坑：`doodle-panel button:last-child` 匹配到的
**不是**「完成」按钮 —— 面板里有 `v-if` 的 `<svg class="doodle-layer">`
和笔刷色板 `<i>`，`last-child` 是「所有子节点里最后一个」，
改用 `last-of-type`（同标签内最后一个）才对。

### 16.7 同一个坑踩了两次：夹具不能手抄

「漏 token → `var()` 断链 → 声明被丢弃 → 静默失效」这个坑
在 `scan-panels.mjs` / `ask-doodle-buttons.mjs` / `theme-bridge.mjs`
三处手抄夹具上**踩了两次**。第二次漏的是
`button-contrast-fill` / `switch-thumb` / `interactive-bg-hover` /
`state-error-primary` 这几个 alias → `.doodle-panel` 的「完成」按钮底色
变成**透明**（`rgba(0,0,0,0)`），扫描器报了一个查了三轮才定位的假「对比度 1.13」。

根因不是粗心，是**手抄 40 个 token 迟早还会漏第三次**。
修法：新增 `.workbuddy/verify/dsh-tokens.mjs` 从
`F:/DSH/resources/app.asar` 真身自动抽取（实测 **19/19 命中**），
再用 `use-shared-tokens.mjs` 把三处手抄夹具全换掉。

### 16.8 断言要逐条反向验证过才算数

B10 新增 23 条 `PANEL_COVERAGE` 断言，格式为
`[说明, 选择器片段, 该规则必须声明的属性]`。

**第一次写错**：只锚定选择器。实测 23 条里有 **14 条是虚的** ——
同一选择器在文件里出现多次（`.generate-pill` 既有合并规则又有 `:hover`，
`.library-item` 有 `{}` / `:hover` / `:disabled` 三条，`.danger` 有两条），
删掉其中一条另一条仍满足断言，被误判成「断言没用」。
判据因此改成**同时锚定选择器与它声明的属性**（如 `.generate-pill` + `button-floating-fill`）。

**第二次写错**：B10 的大正则在合并选择器上翻车。
`.generate-pill` 实际写作 `html[...] .generate-pill,\nhtml[...] .generate-cost {`
—— `{` 前面夹着另一个选择器，一步式 `[^{]*` 会越过。判据拆成两步：
① 主题作用域后（不跨 `{`）紧跟该选择器片段；② 命中位置起 200 字内有 `{`。

新增 `.workbuddy/verify/verify-assertions.mjs` 做反向验证：逐条删掉覆盖，
确认对应断言**真的会报红**。删除器也踩了坑 —— 改成
**删掉该选择器所有含该属性的规则**（`dropAllRulesFor`），
且合并选择器的匹配行末尾没有 `{`，起始行要往后找 8 行找第一个 `{`。

> 第一版验证器 spawn `smoke-test.mjs` 每删一条跑一遍（18 轮），
> 超时 `SIGTERM` 导致 `finally` 来不及还原，**实测把 `dsh-shell.css` 改坏了**
> （删掉了 `.generate-model-menu` 覆盖）。第二版改成把断言逻辑原样抄一份
> 在验证脚本里跑 —— 只读文件 + 正则，零外部依赖、毫秒级。
> **全绿但拦不住的断言比没有断言更危险**，它给人虚假的安全感。

### 16.9 顺带修的构建 bug

`build/tools/install-embed.mjs` 的 `GENERATED = ['index.html', 'assets', 'library-assets']`
里 `library-assets` **整目录删** → 用户素材（实测 6MB 预览图）被占时
`rmSync` 抛 `ERROR ... Error during a 'trash' operation` → **整个安装中断，
但 vite 已构建成功**，产物停在「dist 是新的、embed 是旧的」这种最难查的状态。

改成：`REPLACE_DIR = ['assets']`（整目录删，但删不掉就**跳过不中断**）；
`library-assets` 走 `walk()` 的**按文件名覆盖**；`walk()` 先比
size + mtimeMs，一致就跳过；单文件 `cpSync` 失败只 warn。
输出加一行「跳过 N 个未变化的文件（避免覆盖被占用的素材）」。

## 17. P2.8：左下 / 右下工具条去掉浮岛

### 17.1 用户反馈与真实根因

> 「左下角和右下角的图标按钮功能不要浮岛样式，底部中间的保持不变」

这不是「再加一条样式」那么简单 —— 查上游 `canvas-chrome.css` 947 / 964 行才看清，
**是 P2.5 把上游的设计意图改掉了**。上游原文：

```css
/* 左下角：资产库 / 素材 / 积分。与右下角同款：透明底、按钮簇直接坐画布上。 */
.canvas-page .ref-bottom-left {
  background: transparent;
  ...
}
```

上游注释写得很清楚：左右两组本来就是**裸图标钮**（`background: transparent`），
**只有中条 `.ref-create-bar` 是浮岛**（`#22242b` + 描边 + 圆角 15px + 阴影）。
P2.5 那一轮为了解决「浅色下裸按钮糊在浅底上看不清」，把三组统一成了
同权重的 `bg-layer-1` + 发丝描边 + 圆角 + 阴影 —— 结果：

1. 给裸按钮簇套了三个**没必要的白盒子**；
2. 把「主入口 / 次级工具」的**层级差**抹平了（中条是主操作，本该更重）。

> 这是一个**过度修复**：症状（浅底上看不清）是真的，但病因不是「缺容器」，
> 而是「缺 hover 反馈 + 图标对比度」。加容器是错药。

### 17.2 改法

把三组的合并规则拆开，中条保留浮岛，左右显式打回透明：

```css
.canvas-page .ref-create-bar {
  background: var(--dsw-alias-bg-layer-1);
  border: 1px solid var(--dsw-alias-border-l1);
  border-radius: var(--canvas-radius-sm);
  box-shadow: var(--canvas-shadow-float);
}

.canvas-page .ref-bottom-left,
.canvas-page .ref-bottom-right {
  background: transparent;
  border: 0;
  box-shadow: none;
  color: var(--dsw-alias-label-secondary);
}
```

**显式写出来**而不是「上游恰好是 transparent」，理由有两条：
① 不依赖上游（上游改了我们也不慌）；② 意图显式，读代码的人看得见。

### 17.3 连带必改：hover 底色要从「实心」换成「半透明」

容器透明之后，按钮的 hover 底色**不能沿用** `bg-layer-2` ——
它是**实心**层（浅 `#f5f6f7`），压在纯白 `bg-base` 上几乎看不见，
等于把 hover 反馈一起去掉了。改用官方专门为「透明底上叠一层」设计的
半透明交互色：

| 状态 | 改前 | 改后 |
|---|---|---|
| hover | `bg-layer-2`（实心） | `interactive-bg-hover`（浅 `#2631480f` / 深 `#ffffff14`） |
| 激活 | `bg-layer-2`（实心） | `interactive-bg-active`（浅 `#2631481a` / 深 `#ffffff24`） |

`interactive-bg-*` 是 **alpha 色**，叠在任何底色上都成立 —— 这正是它存在的意义。
中条是浮岛（`layer-1` 实底），继续用 `bg-layer-2` 才对，所以两条规则分开写。

### 17.4 踩坑：改 overlay 后用 `build:only` 会静默不生效

第一次改完跑 `npm run build:only`，产物 CSS 哈希**没变**
（还是 `style-DBFXSH2g.css`），grep 新规则命中 0 —— 改动根本没进去。

原因：`build:only` 只跑 `vite build`，**不跑 `sync-upstream.mjs`**。
而真正被 `main.ts` import 的是 `build/src/dsh-shell.css`（镜像产物），
不是 `build/overlay/src/dsh-shell.css`（我们的编辑源）。
overlay 要靠 sync 才会覆盖到 `build/src/`。

`sync-upstream.mjs` 的文件头注释里已经写了这个坑（「改完 overlay 必须走完整 build」），
但注释里同时写着「`npm run build:only` 的适用场景只有『只改了 `build/src/` 之外的东西』」
—— 这句**自相矛盾**（改了 overlay 就是改了 `build/src/` 之外的东西），
实测按字面理解会踩。已按正确语义执行 `npm run build`，
产物哈希变为 `style-BQZLuWpk.css`，新规则命中。

> 教训：验证「改动有没有进产物」要**先看产物哈希变没变**，不要凭「构建成功」判断。
> `vite build` 永远会成功，构建器不知道你改的是不是它编的那份文件。

### 17.5 断言改法：从「三组一致」翻成「层级差存在」

B10 ⑧ 原有一条断言要求三组工具条在**同一条规则**里拿阴影 ——
它现在会报红，因为这条断言本身被用户决策推翻了。
改成断言**层级差存在**（3 条）：

```js
// 中条必须有浮岛阴影
assert.ok(/\.canvas-page \.ref-create-bar\s*\{[^}]*box-shadow:/s*var/(--canvas-shadow-float/)/.test(outsideMedia), ...);
// 左/右必须显式打回透明
assert.ok(/\.canvas-page \.ref-bottom-left,\s*\.canvas-page \.ref-bottom-right\s*\{[^}]*background:/s*transparent[^}]*box-shadow:/s*none/.test(outsideMedia), ...);
// 透明容器上的 hover 必须用半透明交互色
assert.ok(/\.canvas-page \.ref-bottom-left button:hover,\s*\.canvas-page \.ref-bottom-right button:hover\s*\{[^}]*interactive-bg-hover/.test(outsideMedia), ...);
```

**反向验证**：删掉那 3 行透明声明后，测试确实报 `37 通过 / 1 失败`，
错误信息正是「左下 / 右下的工具条没有显式打回透明」。

> 断言被需求推翻时，要**改断言而不是绕过它**。
> 同时留一条注释记清「为什么推翻」+「上游原文是什么」，
> 免得半年后有人看到 P2.5 的注释和 P2.8 的代码打架。

### 17.6 新增验证脚本

`.workbuddy/verify/shot-bars.mjs` —— 拍底部三组工具条在**浅色 / 深色**两档下的样子。

为什么不用现成的 `shot.mjs`：它**不注入 DSH 主题桥**（没有 `--theme` 参数），
而画布的浅色是靠宿主 `postMessage` 写 `data-dsh-theme` + 一整套 `--dsw-*` token

这个脚本走 `client.js` 发的**同一条消息**，并顺带用 `getComputedStyle`
把三组的 `bg` / `border` / `shadow` 打出来 —— 截图是「看」，这里是「量」。

## 18. P2.9：画布菜单（顶栏下拉 + 右键菜单）浅色化

### 18.1 用户反馈与误判

用户发来**真实 DSH 窗口截图**（这是本项目第一次拿到真实环境的证据），
浅色主题下画布中央有一块深底白字的浮层。

第一反应是「上一轮漏了 `.generate-panel`」。**这是误判** —— 用探针实测：

```
generate-panel  生效底色 rgb(255,255,255)   ← 已经白底了，覆盖层赢了
```

截图里那块深色是**另一个元素**。认错目标的原因很具体：
我是按「哪个面板没被覆盖」去查的，而「面板」这个假设本身就是错的。

### 18.2 真实根因：两个元素，且都是「没写」不是「写错」

新建 `.workbuddy/verify/scan-whole-page.mjs`（**不预设任何类名**，
只按「实底 + 亮度不对 + 面积够大」扫全页，按面积排序），扫出两块：

| 元素 | 实测底色 | 上游值 | 根因 |
|---|---|---|---|
| `.canvas-menu-card`（顶栏画布菜单） | `rgb(34,36,43)` | `#22242b` | 覆盖层里**一次都没出现**这个选择器 |
| `button.ref-title`（菜单触发钮） | `rgb(37,40,48)` | `#252830` | 上游 `[aria-expanded="true"]` 规则 |

**为什么之前的 7 面板扫描没抓到**：

1. 它们不在那 7 个 `v-if` 面板清单里 —— `CanvasView.vue` 里
   `projectMenuOpen` 是**另一个**状态变量，与 `activePanel` 并列；
2. 它们挂在 `header.ref-topbar` 里，**不在 `.canvas-stage` 内**；
3. 之前只扫「默认状态」，而它们默认**不在 DOM 里**。

### 18.3 顺带发现：还有一个同款漏网的

`.canvas-context-menu`（画布右键菜单）是**同一套配色**——
上游 `canvas-chrome.css` 1238 行自己的注释写着
「与 `.canvas-menu-card` 同一套：#22242b 平涂 + #383b45 发丝边 + 12px 圆角」。

只改卡片不改菜单 = 还是一块黑斑。用一个合并选择器一次覆盖两处。

### 18.4 最隐蔽的一处：`[aria-expanded="true"]`

`.ref-title` 的深色**不是 hover**，是**展开态**：

```css
/* 上游 canvas-chrome.css 700 行附近 */
.canvas-page .canvas-project-menu .ref-title[aria-expanded='true'] {
  color: #fff;
  background: #252830;      /* 特异 (0,4,0) */
}
```

我最初只写了 `.ref-title:hover`，压了两次都没生效。
新建 `.workbuddy/verify/why-loses.mjs`（把全部命中规则按
**特异性 → 源码顺序**排序，标出谁赢）才看清：
我那条规则的特异性是 (0,5,0)，**本来能赢**，
但 `el.matches(':hover')` 当时是 `false` —— **状态就没匹配上**，压根没参与竞争。

> 这是本项目第三次栽在「状态」上（前两次：`v-if` 未打开、`nth-child` 定位错）。
> 扫描器只看「当前生效值」不够，还要报「**当前处于什么状态**」。

修法：展开态与 hover 态**分别**覆盖，且都带上 `[aria-expanded]` / `:hover` 本身
把特异性提上去：

```css
html[data-dsh-theme] .canvas-page .ref-title[aria-expanded='true'] {
  background: var(--dsw-alias-bg-layer-2);
  color: var(--dsw-alias-label-primary);
}
html[data-dsh-theme] .canvas-page .ref-title:hover {
  background: var(--dsw-alias-interactive-bg-hover);
  color: var(--dsw-alias-label-primary);
}
```

展开态用**实心** `bg-layer-2`（按钮浮起，明确表示「现在开着」），
hover 用**半透明** `interactive-bg-hover`（容器透明，只能叠一层）——
判断标准还是那条：**hover 底色是实心还是 alpha，取决于下面有没有实底**。

### 18.5 内部构件的覆盖

`.canvas-menu-card` 一整套深色硬编码（上游 745–897 行）：

| 上游 | 覆盖为 | token |
|---|---|---|
| `#22242b` 底 | `bg-layer-1` | 两主题 |
| `#383b45` 描边 | `border-l1` | 两主题 |
| `0 16px 44px #000a`（67% 黑） | `--canvas-shadow-float` | 两主题 |
| `#2e313a` 分隔线 | `border-l1` | light |
| `#6f7581` eyebrow / label | `label-tertiary` | light |
| `#fff` 画布名 | `label-primary` | light |
| `#777c87` 统计 / 次要 | `label-secondary` | light |
| `#d5d8de` 列表项文字 | `label-primary` | light |
| `#2c2f38` 列表项 hover | `interactive-bg-hover` | light |
| `#8e95a1` 动作图标 | `label-secondary` | light |

⚠️ **阴影必须两主题都写**。只写 light 的话深色下菜单反而成了唯一没收拾的浮层
（实测深色下上游那条 `rgba(0,0,0,0.667) 0 16px 44px` 糊成一团）。
底色 / 描边同理 —— `#22242b` 不对应 DSH 任何一层（`bg-layer-1` 深色是 `#232324`），

### 18.7 同一个坑连踩三次：模板字符串里的引号

写 CDP 探针时页面代码放在 JS 模板字符串里，任何未转义的引号都会
**提前闭合外层模板** → Node 侧 SyntaxError，而**报错指向注释那一行**：

| 次 | 写了什么 | 报错 |
|---|---|---|
| ① | 注释里 `[aria-expanded="true"]` | `Invalid left-hand side in assignment` |
| ② | `el.matches(':hover')` 的单引号 | `SyntaxError: Unexpected identifier` |
| ③ | 注释里 `` `#4176e6` `` 的反引号 | `Invalid or unexpected token` |

三次的报错都指不到真正的原因。修法两条：

1. **CDP 异常要把详情取出来**（技能 §3.12 早就记了「`Runtime.evaluate`
   不会因页面抛异常而 reject」，但我第一版只取 `exceptionDetails.text`，
   它就一句 `Uncaught`）—— 要取 `exception.description` + `lineNumber`，
   第二次就靠行列号直接定位到第 98 行；
2. **写静态检查**（`check-template-quotes.mjs`），
   扫「模板字符串范围内 + 注释行 + 含引号」这个组合，毫秒级，可挂测试。

顺带修掉一个自己踩的：中文标识符 `祖先 expanded` **带空格** → SyntaxError。
中文键名合法，但**不能含空格**。

## 19. P3：节点卡浅色化 + 全量穷举补漏（2026-10-02）

### 19.1 用户反馈

> 创作板还是有问题帮我优化，整体再帮我检查一下代码，有哪些需要优化的全部帮我优化

两条诉求：**① 创作板必须修好**（§18.9 里明确挂着的未做项）；**② 不只修这一处**，
要主动检查一遍代码、把所有该优化的都优化掉。

### 19.2 第一个根因：节点卡是 localStorage 驱动的，不种数据就永远扫不到

新一轮实测（种 13 种节点后逐卡扫）的结果是 **11 张卡全部深底** —— 而这个
问题已经跟着三张用户截图存活了三轮。

原因是节点卡有两道门槛，任一不成立它在 DOM 里就压根不存在：

1. **localStorage 驱动**：项目数据存在 `nexusvault-canvas-project.<id>` 里，
   空画布一张卡都没有，`v-if` 直接不渲染。
2. **加节点面板（`.asset-panel`）是个悬空入口**：它在 JS 里被 `v-if` 或某些
   状态挡着，没有任何按钮能让它出现在 DOM 上，所以「点 UI 把节点加出来」
   这条路根本走不通。

前三轮用的 `scan-whole-page.mjs` 是**不预设类名**地全页扫，理论上应该能扫到。
但它扫的是**空画布**——因为没种数据，节点卡一张都不在。

解法：`.workbuddy/verify/scan-all-nodes.mjs` —— 先往 localStorage 种一个含全部
13 个 type 的项目，刷新、等 `v-if` 生效，再逐卡读计算样式：

```js
localStorage.setItem('nexusvault-canvas-projects', JSON.stringify([...]));
localStorage.setItem('nexusvault-canvas-active-project', 'verify-all-nodes');
localStorage.setItem('nexusvault-canvas-project.verify-all-nodes', JSON.stringify(SEED));
```

> **这是本项目第四次栽在「状态」上**（前三次是 `v-if` / `nth-child` /
> `aria-expanded`）。规律：凡是要靠用户先做点什么才出现的内容（展开、hover、
> 选中、从 localStorage 恢复），不先把状态造出来就只能瞎猜。

### 19.5 最重要的一条：**换底必须连带换字**

容器一变白，原本写死的浅色字就直接隐形。这和深底色不同 —— 它不是一块突兀的
深色，是一片「什么都没有」，更隐蔽也更难自查。查出来的三处：

| 选择器 | 上游 | 为什么看不见 |
|---|---|---|
| `.panel-search input` | `color: #fff` | 容器变白后白字 = 没有，打字才看得到字 |
| `.generate-model-option.selected` | `color: #fff`，**且没有自己的 background** | 透出的是后面那张已变白的菜单 —— 选中当前模型时那一行会整行消失，只剩蓝勾浮着 |
| `.canvas-text-size` | `color: #e6e8ee`，自身 `background: transparent` | 透出的是已变白的工具条底 |

判断要点：**一个元素自己没有底色，不等于它安全 —— 要看它实际透出的是谁的底。**

### 19.6 第二个根因：前三轮都是「看到一处改一处」

三轮修复全部由用户截图驱动：截图打到哪，改到哪。致命之处是**永远不知道还剩
多少**，只能等下一张截图。

解法是反过来：不靠眼睛，靠穷举。`.workbuddy/verify/scan-dark-gap.mjs` 把上游
4 份画布 CSS **全量**过一遍，只挑会露馅的字面量，再拿选择器去覆盖层比对：

- **维度一 · 深底色**：底色类属性（`background` / `border*` / `box-shadow`）里
  不透明、相对亮度 < 0.30 的（约 `#777` 以下）。alpha 色不算，它自适应。
- **维度二 · 浅色文字**：`color` 里不透明、相对亮度 > 0.75 的。**方向故意相反**
  —— 底色挑暗的，文字挑亮的。

结果：**119 处深底色 + 63 处浅色文字，缺口全清 0。**

### 19.7 扫描器自己踩的坑（每一处都会导致假结论）

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| ① | 只扫底色 | 一开始只写了维度一，63 处隐形白字一条都看不到 | 加维度二，阈值反向 |
| ② | 取「最后一段」当 key | `.panel-tabs b` 的最后一段是 `b`，单字母无区分度 | 取**最后一个类选择器** |

- 主题三态在**真实 DSH 窗口**里的表现 —— 服务鉴权且不开 CDP，只能靠用户肉眼确认。

### 19.13 这一轮最该记住的

> **不要写「永远绿」的断言。** 挂进测试之前，先删掉被测的那段代码确认它会变红。
